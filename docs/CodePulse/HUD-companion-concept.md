# CodePulse HUD 副驾概念

## 文档状态

| 项目         | 内容                                     |
| ------------ | ---------------------------------------- |
| 性质         | 实验性派生设计，不替代上游正式产品定位   |
| 代码基线     | CodePulse `v1.3.3` / `a5d0c00`           |
| 工作分支     | `codex/hud-companion-concept`            |
| 设计参照     | GroundControl `e69c07a`                  |
| 主要目标     | 把桌面端从“被呼出的面板”转为常驻副驾 HUD |
| 本分支非目标 | 改写设备协议、固件或既有历史统计数据语义 |

这份文档定义当前概念分支的设计契约，也标明派生版在代码管理和正式发布前必须完成的
隔离工作。它不是上游 `main` 的发布说明。

## 来源与可复用边界

本设计观察了 GroundControl `e69c07a` 的 HUD 实现，借鉴的是一个窗口合成原则：

- 原生窗口维持每像素透明，并把窗口整体 opacity 固定为 `1`；
- 只调整面板背景的 alpha，让底色透明而文字继续以完整不透明度渲染；
- 由无边框、置顶、不抢焦点的窗口承担“随时待命”的副驾角色。

本分支没有复制 GroundControl 的 PyQt 代码、鹦鹉素材、图标或其他视觉资产；Electron、
React 与 CSS 实现均在 CodePulse 代码结构内独立完成。CodePulse 的 `LICENSE` 为 MIT；
GroundControl 的项目元数据与 README 也声明 MIT。若以后开始复制具体代码或素材，应重新
核对来源文件的授权，并在派生版本中保留许可证与必要的归属说明。

## 设计原则

### 1. HUD 是主界面，不是通知的附件

系统通知和短暂 toast 会把注意力带回主屏，也可能被系统策略折叠、延迟或清除。HUD
方案把副屏本身当成持续可见的提示介质：普通活动安静存在，需要用户时再提升视觉权重。
桌面端不再创建原生系统通知。

### 2. 状态丰富，颜色克制

运行时仍保留完整状态机和五个 HUD 语义层级，但颜色不与每一种状态一一绑定。日常状态
统一使用中性色；橙色是唯一的注意颜色，并覆盖整个项目块。状态文字、图标和时间信息
负责解释“为什么变橙”，颜色只回答“现在是否值得看”。

| HUD 层级 | 运行时映射                                     | 颜色层级 | 用户含义           |
| -------- | ---------------------------------------------- | -------- | ------------------ |
| `quiet`  | `idle`、`cancelled`，以及已经确认的终结状态    | 中性     | 不需要处理         |
| `active` | `prompt_submitted`、`thinking`、`tool_running` | 中性     | 正常工作中         |
| `notice` | 未读的 `done`                                  | 橙色     | 已完成，值得看一眼 |
| `action` | `waiting_permission`、`waiting_user_input`     | 橙色     | 正在等用户明确操作 |
| `fault`  | 未读的 `error`、`timeout` 或 `usage_limited`   | 橙色     | 工作受阻，需要检查 |

`notice`、`action` 与 `fault` 是语义差异，不是三种新颜色。这样既保留状态准确性，又避免
蓝、黄、绿、红同时竞争注意力。

### 3. 用量仍是常驻信息，但不是最高注意层

项目卡中的上下文占用继续显示；账户配额压缩为一条可关闭的底部摘要，不再为 provider 建立
大面积额度面板。常规进度采用中性色；接近耗尽时可以借用橙色，但不会再为不同 CLI 或不同
图表分配互相竞争的品牌色。HUD 首先回答“谁需要我”，其次才回答“用了多少”。完整历史仍由
本机 SQLite 与统计后台承载。

## Project Deck 信息架构

- 项目是主层级。Claude Code、Codex、Grok 与 Kimi 只作为项目卡顶部的小型来源元数据。
- 同一工作区被多个 CLI 使用时合并为一张卡，并显示类似 `CLAUDE · CODEX` 的来源摘要。
- quota-only provider 可以进入底部用量行，但不会生成空项目区或空状态插画。
- 默认使用一个全局单列，项目按等待介入、未读故障/完成、运行中、空闲排序；紧凑双列矩阵
  保留为可选布局。
- 项目卡只保留来源、状态、名称、活动/时间和可用时的上下文细线；不再重复模型、思考深度、
  耗时等多组统计瓷砖。
- 未读项目保留明确的“已读”按钮。授权或输入等待即使没有未读标志也持续橙色，直到运行时状态改变。
- 主 HUD 不放语言、静音、统计和设置按钮；低频管理入口位于托盘。

## 窗口与副屏策略

- 窗口使用透明、无边框、置顶、跳过任务栏的 Electron `BrowserWindow`。
- 优先选择主屏右侧最远的显示器；没有右侧显示器时选择其他副屏，最后才回退到主屏。
- 初始位置位于目标显示器右上角并留出边距；默认宽度约 `640px`。渲染器测量标题、项目行和
  用量行的自然高度并回传主进程，使透明原生窗口随项目数量伸缩；超过工作区时才进入滚动。
- 状态触发的显现使用不激活窗口的方式，不夺取正在编辑或终端窗口的焦点。
- 用户从托盘明确打开 HUD 时，可以正常聚焦并操作确认和统计后台；“HUD 设置”打开独立的
  普通 `BrowserWindow`，不再作为透明置顶 HUD 内的弹层。
- 所有项目进入一个全局流，不存在 provider 内部滚动。橙色项目按注意力优先级排到前方，并在原卡片
  内保留摘要与确认入口，不再额外复制一条“全局注意带”。
- 原生窗口 opacity 保持 `1`；HUD 设置只改变面板 RGBA alpha，以保证黑字或白字清晰。
- 新安装默认采用浅色黑字 HUD，仍保留深色与自动外观。

当前透明度范围为 20%–100%，默认 92%。橙色注意效果可选常亮、呼吸和脉冲；系统请求
减少动态效果时停止动画。安静模式持续 30 分钟，并把动画收束为常亮，而不是隐藏状态。

## 未读、确认与提示寿命

过去的短 TTL 适合 toast，却不适合放在副屏上的持久提示。当前策略是：

1. 未读的完成或故障状态不因常规 TTL 自动消失；
2. 用户在项目块中确认（ack）后恢复正常清理；
3. 新一轮任务也可以替换上一轮终结状态；
4. 明确的授权/输入等待始终属于 `action`，不依赖“未读”标志。

因此，“橙色还在”具有稳定含义：用户尚未处理，或任务仍在等用户。它不是一次已经错过的
系统弹窗。托盘只聚合成中性 / 橙色两档，不重新创造另一套颜色语言。

## 墨水屏与设备端边界

橙色和动效属于桌面渲染投影，不进入领域状态机，也不是设备协议的语义。设备端继续消费
版本化、只读的状态与用量数据；本分支不修改现有 LAN device API 或固件。

在单色墨水屏上，`notice` / `action` / `fault` 应映射为反白块、粗边框、图案或稳定图标，
而不是依赖橙色；呼吸和闪烁也不应直接移植，以免产生无谓刷新、残影和耗电。未来如果设备
需要五级语义，应传递抽象层级或既有运行时状态，由每种屏幕自己选择表现形式。

## Windows 低 I/O 运行边界

HUD 的实时性默认来自 CLI hooks，而不是持续遍历用户的全部会话历史。桌面端启动时仅执行一次磁盘
恢复，随后关闭递归目录监听、启动补扫和固定周期的全量 session sync；系统休眠恢复或显式刷新仍可
触发一次受控同步。打开 HUD、设置或统计后台只复用内存快照，不再触发 session 扫盘。Renderer 也不在
窗口加载时重复扫盘。

Codex 已绑定用量文件的兜底刷新由 12 秒放宽到 60 秒。确实需要旧版持续扫描行为时，可在启动环境中
设置 `CODEPULSE_BACKGROUND_SESSION_SYNC=1`；该模式会增加磁盘元数据访问，不应作为 Windows HUD
默认值。性能验收需要同时检查 Electron 进程、端口、磁盘队列和 Explorer 文件操作延迟，而不只检查
界面帧率。

## 当前限制与下一阶段

- 设置已经与 HUD 分离为独立窗口；统计后台仍复用 HUD 渲染窗口，后续可继续拆分低频管理表面。
- 初始位置尚未按用户拖动结果持久化，也未在显示器热插拔后自动重新锚定。
- 仓库中的截图仍是 `v1.3.3` 基线，需要在 HUD 视觉稳定后重新采集。
- 当前只有全局注意效果和 30 分钟安静模式，尚无按项目 snooze、优先级或不同提醒策略。
- 托盘只表示总体是否需要注意；HUD 才是项目级详情来源。
- 本分支没有扩展设备协议、固件渲染或设备端支持的 CLI 范围。

## 专业的 Git 远端与分支管理

上游仓库不属于派生版维护者，因此应把“读取上游”和“推送自己的代码”分成两个远端：

- `upstream`：`https://github.com/noeigenstate/CodePulse.git`，只用于获取原项目更新；
- `origin`：自己控制的 fork 或私有仓库，用于推送概念分支、PR 与派生版标签。

当前仓库若仍把上游叫作 `origin`，应在自己的 fork 准备好后执行一次远端整理：

```bash
git remote -v
git remote rename origin upstream
git remote add origin <your-fork-url>
git fetch --all --prune
git push -u origin codex/hud-companion-concept
```

在 fork 建好之前不要提前重命名，也不要把概念分支推向没有写权限或并不属于自己的上游。
日常同步建议显式执行 `git fetch upstream`，然后由维护者选择在概念分支上 rebase 或 merge
`upstream/main`；不要自动改写已经共享的历史。

推荐工作流：

1. `main` 只跟踪已审查的上游/派生版稳定点，并启用分支保护；
2. 每个概念在独立 `codex/...` 或 `feature/...` 分支开发，提交保持小而可解释；
3. 先向自己的 fork 提 PR，CI 通过并完成视觉验证后再合并；
4. 是否向原项目提交上游 PR，与派生版自身发布分开决策；
5. 保留 MIT 许可证、上游来源和基线 commit，派生版使用自己的变更日志与版本标签；
6. 原型期使用 pre-release/nightly，不把实验构建伪装成上游正式 CodePulse。

## 派生版正式发布前的隔离清单

当前概念分支适合本地实验，但不应直接作为与上游并存的正式安装包发布。至少完成以下检查：

1. **应用身份**：更换 `appId`、`productName`、可执行文件名和安装包标识，避免操作系统把
   两个产品视为同一个应用。
2. **更新源**：`apps/desktop/src/main/update-checker.ts` 仍指向
   `noeigenstate/CodePulse`。派生版必须使用自己的签名发布源或明确禁用自动更新，否则可能
   被上游二进制覆盖。
3. **userData 隔离**：相同产品身份会共享设置、SQLite、更新 snooze 和设备凭据。正式版需
   使用独立目录，并设计一次性、可回滚、先备份的迁移；不能直接抢占上游数据目录。
4. **Hook 与端口隔离**：现有 hook 默认写向 `127.0.0.1:17888`，设备服务默认使用
   `17889`。两个版本并存会争抢端口和 CLI 配置所有权；应为派生版定义独立端口、环境变量、
   managed hook 标识以及卸载边界。
5. **设备发现与密钥**：检查 mDNS 服务名、配对 ID、device token 和持久化路径，确保派生版
   不会误连或删除上游设备配置。
6. **品牌与支持边界**：安装包、关于页、仓库链接、问题反馈和隐私说明都要指向派生项目，
   同时清楚标注基于 MIT CodePulse，而不是原作者发布的官方版本。
7. **共存测试**：至少覆盖先装上游/后装派生版、反向安装、同时运行、分别卸载、数据库迁移
   失败回滚和更新失败回滚。

只有应用身份、更新、数据和 hook/端口四个核心边界都隔离后，才适合推送正式 release；在此
之前应把该分支视为可撤销的设计实验。
