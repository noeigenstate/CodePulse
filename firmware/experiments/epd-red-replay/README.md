# 红色导致连续全刷：生产代码回放

这是 **host 软件复现程序**。直接编译当前 `quiet_dashboard.c`、
`display_sync_policy.c`、字体和生活卡渲染器；替换的只有两个面板传输入口。
不连接串口、启动客户端、改变配置、刷机或操作物理屏幕。

它回答：哪些输入真正进入刷新决策、哪些像素变了、代码选择了什么刷新路径。
它不能证明红色在黑白局刷后会保持、无残影、物理时序正确或面板寿命合格。

## 运行

从仓库根目录运行（PowerShell 7、MSVC C 编译器）：

```powershell
pwsh -NoProfile -File firmware/scripts/repro-red-refresh.ps1 -Iterations 40 -Rounds 3 -AllowExistingShadowWarning
```

默认输出到根目录忽略的 `.tmpshots/red-refresh-replay/`，可用 `-Output` 指定另一个
目录保留多轮对比。`Iterations` 是每个独立场景的更新次数；`Rounds` 是重建基准后
重放的轮数。每个场景都覆盖普通、反色两种显示，并在每次事件后立即重复相同请求。
Debug 与 `NDEBUG` 各跑一遍，所有检查使用不会被 `NDEBUG` 移除的 `CHECK`。
两份逐步 CSV 必须字节一致，源码在运行前后必须保持同一哈希。

`-AllowExistingShadowWarning` 是当前源码的临时诊断开关，只在编译
`life_dashboard.c` 时允许已有 MSVC C4456（第 815 行局部 `n` 遮蔽第 774 行的 `n`）。
其他文件及其他警告继续按 `/W4 /WX` 检查。默认不忽略该警告；修好上游警告后应去掉
这个参数。此程序不会修改生产源码来绕过编译失败。

后续修复可以用相同输入明确检查“红色不变时仍发生全刷”是否消失：

```powershell
pwsh -NoProfile -File firmware/scripts/repro-red-refresh.ps1 -Iterations 40 -Rounds 3 -AllowExistingShadowWarning -RequireNoStaticRedFull
```

普通模式退出 0 只表示回放完成、输入及传输历史检查成立，**不代表刷新问题修复**。
验收模式发现红色逐字节不变而黑白变化的全刷时退出 2；编译/输入/历史不一致另报错。
验收目标包含变化矩形包围红色的难例，不能通过删除驱动红色保护、丢掉目标更新、
把红色直接清掉或伪造计数来满足。实机允许哪些局刷范围还需要另做物理验证。

## 场景

| 名称 | 输入与用途 |
| --- | --- |
| `bw-work` | 无红色的任务页，只改另一任务的黑色标题；局刷对照 |
| `static-red-work` | 保留待确认红色任务，只改另一任务的黑色标题 |
| `red-work-change` | 待确认与异常交替，真实红色像素发生变化 |
| `static-red-card` | 图片卡红色固定，只改远处一个黑像素；新 ID 明确提交更新 |
| `red-card-change` | 只移动红点，检查黑白不变时仍能识别红色变化 |
| `held-red-card` | 同一 ID 的卡片内容改变，确认生产调度器继续冻结当前卡片 |
| `calendar-bw` | 月份和日期红色固定，只改黑色电池图标；新 ID 请求更新 |
| `life-bw` | 股票卡红色固定，只改黑色来源文字；新 ID 请求更新 |
| `red-reentry` | 清红、冷却内重新进入、再离开、恰好 120 秒的新事件进入 |
| `red-in-dirty-window` | 两处黑白变化包围不变的红点，区分红色落在窗口内的难例 |
| `same-pixels-new-id` | 新 ID 但像素完全相同，确认渲染后也不发送刷新 |

卡片场景的 ID 是明确构造的触发条件，不意味着真实日历/生活卡每次传感器变化
都会刷新。更新先经过 `display_sync_evaluate` 和 `display_sync_project`；保持相同
ambient ID 时的抑制独立验证，没有绕过调度器制造高频自动刷新。

## 输出与解释

- `source.json`：根提交、参数、被编译的生产源码及头文件 SHA256。
- `debug/steps.csv`、`ndebug/steps.csv`：每一步的调度原因、刷新模式、黑/红变化像素数、
  当前/目标红像素、变化矩形、窗口内旧红像素数、折色与基准标记。
- `summary.csv`：各场景更新、全刷、局刷、无变化、调度抑制及折色次数。
- `run.log`、`compile.log`：运行及编译原始输出。
- `*.ppm`：首轮各模式的基准/第一次更新实际交给传输入口的 400×300 双色图。

`red_diff_pixels` 是逐字节 XOR 后的精确像素差异，不依赖生产代码中的红平面哈希。
变化窗口由黑白差异计算，水平按字节对齐且至少 16px；这只是候选窗口几何，
**不是当前全刷函数实际下发了局部窗口**。`red_in_bw_window` 用于后续实机分组。

`logical_completion_ms` 来自模拟时钟。传输替身分别加上人为固定的 16000/3000ms，
只为验证完成时间后的冷却状态，绝不将它当作实机刷新耗时。每一步都在前一笔模拟
传输完成后开始；冷却场景每四步显式跳到边界，并仍需新的输入事件。

## 2026-11-05 基线结果

根提交 `ca3efd7a8aa4516ebd0bd00a36ac7a0ca74d486f` 的生产刷新相关源码，
40 次更新 × 3 轮 × 普通/反色 × 11 场景，每个构建模式：

- 2640 次事件更新、2640 次相同请求复查、66 次独立启动基准，共 5346 条明细。
- 纯黑白任务：240/240 次局刷、0 次运行时全刷。
- 不变红色 + 黑白更新：5 类场景共 **1200/1200 次运行时全刷**；其中 960 次的
  黑白候选窗口没有红点，240 次的候选窗口包围红点。
- 红色实际变化：任务和图片卡各 240/240 次全刷，独立于上述不变红色问题。
- 同 ID 卡片：240 次调度抑制；新 ID 同像素：240 次无面板操作。
- 进入/离开/冷却边界：120 次全刷、120 次局刷、60 次红色折为黑白。
- Debug/NDEBUG 两份逐步输出完全一致。短序列验收模式按预期报告失败。

根因定位：`main/quiet_dashboard.c` 在像素确有变化后，只判断
`has_red || s->previous_has_red` 就调用三色全刷；120 秒限制只适用于当前已无红色
时重新进入红色。`main/driver_quiet.inc` 则拒绝所有非空红平面，其黑白路径将红 RAM
用于 NEW 数据。因此不能只放宽上层条件就宣称红色局刷已支持。

原有检查单独记录：四组 PAIR/窗口驱动与生命周期测试通过；完整
`test-quiet.ps1` 默认停在上述 C4456，临时允许该警告后又停在
`tests/quiet/test_dashboard.c:180` 的旧局部刷新范围断言。没有将这些基线失败改成
通过，也没有将整套现有回归标为通过。生产双端预览的 75 项源码哈希检查通过。

私有原始回执放在根 `.tmpshots/red-refresh-repro-20261105/`，不提交到源码。
本轮只建立复现基线，未更改生产刷新策略或波形；实体显示效果尚未在本轮验证。
